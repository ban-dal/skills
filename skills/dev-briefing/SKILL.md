# Dev Briefing

구현 품질을 떨어뜨리는 주범은 모델의 능력 부족이 아니라, 사용자의 머릿속에만 있는 정보가
전달되지 않은 채 구현이 시작되는 것이다. 이 스킬은 코드를 쓰기 전에 그 빈칸을 소진하는
프로토콜이다: **Recon → Teach-back → Grill → Plan → Execute**.

## 크기 게이트

모든 요청이 브리핑을 거칠 필요는 없다. 게이트를 매번 태우면 스킬이 방해물이 된다.

- **건너뛴다**: 스코프가 자명하고 변경이 소규모일 때(오타, 한 줄 수정, 명확히 지정된 국소
  변경). 건너뛴다는 판단을 한 줄로 표시하고 바로 구현한다.
- **진행한다**: 새 페이지·기능, 기획서/디자인 첨부, 여러 파일에 걸치는 변경, 수용 기준이
  불명확한 요청. 아래 5단계를 순서대로 밟는다.

## 삼분류

이 스킬의 심장. 작업에 대해 **모르는 것(빈칸)** 을 찾을 때마다 세 갈래 중 하나로 분류하고,
갈래마다 다르게 행동한다:

| 갈래 | 판별 | 행동 |
|---|---|---|
| **Fact** | 코드·기획서·Figma에서 찾을 수 있다 | 조사한다. 사용자에게 묻지 않는다 |
| **Finding** | 기획서에는 있지만 사용자가 모를 수 있다 | Teach-back에서 보고한다 |
| **Decision** | 어디에도 없고 사용자의 기술적 판단이 필요하다 | Grill에서 하나씩 묻는다 |

세 갈래 어디에도 넣을 수 없는 잔여 빈칸은 **가정**으로 기록하고 Plan에 명시한다.
"아무도 모름"도 침묵이 아니라 산출물이다.

## 1. Recon — 묻기 전에 안다

요청·기획서·Figma를 읽고, 코드베이스에서 비슷한 기존 구현(유사 페이지·컴포넌트·API 패턴)을
찾는다. 빈칸 목록을 만들어 삼분류한다. Fact는 이 단계에서 전부 소진한다 — 조사로 알 수 있는
것을 사용자에게 묻는 것은 사용자의 시간을 낭비하는 일이다.

*완료: 모든 빈칸이 Finding / Decision / 가정 중 하나로 분류됨.*

## 2. Teach-back — 기획서를 사용자에게 보고한다

사용자가 기획서를 전달했더라도 그 내용을 완벽히 알고 있다고 가정하지 않는다. 기획서를 읽은
직후에는 에이전트가 사용자보다 스펙을 더 잘 아는 순간이 생기며, 이때 조용히 자기 해석대로
구현하는 것이 가장 흔한 품질 사고다.

요약은 금지다 — 사용자가 이미 아는 것의 반복은 정보가 아니다. **사용자가 몰랐을 확률이 높은
것만** 골라 보고한다:

- 스펙 문서 간 **모순**
- 스펙의 **공백** — 기획서가 답하지 않는 상태·케이스(빈 목록, 에러, 로딩, 권한 없음 등)
- 요청과 스펙이 **어긋나는** 지점
- 기술적 함의가 큰 스펙 디테일(성능·구조에 영향을 주는 요구)

각 finding에 사용자의 반응(알고 있었음 / 몰랐음 / 스펙이 틀림)을 기다린다. finding이
없으면 "기획서에서 특이점 없음"을 한 줄로 표시하고 다음 단계로 간다.

*완료: 사용자가 각 finding에 반응함.*

## 3. Grill — Decision을 하나씩 심문한다

Decision을 **한 번에 하나씩** 묻고, 답을 기다린 뒤 다음 질문으로 간다. 여러 질문을 묶어
던지면 사용자는 대충 답하게 되고, 앞 답이 뒤 질문을 바꾸는 의존 체인을 다룰 수 없다.

- 각 질문에 **추천안**을 붙인다. 백지 질문은 사용자에게 설계를 떠넘기는 것이다.
- 사용자가 "네 판단대로"라고 위임하면 추천안을 채택하고 가정으로 기록한다.

**통과 조건** — 아래가 모두 이미 충족되면 Grill을 생략하되, 생략 판단과 근거를 짧게 표시한다:

- 수용 기준이 "X 하면 Y" 형태로 체크 가능하다.
- 범위 경계가 정해져 있다 — 무엇을 *하지 않는지*가 명시된다.
- 핵심 엣지·실패 케이스가 식별되어 있다.

*완료: 열린 Decision이 0개(답변되거나 명시적으로 위임됨).*

## 4. Plan — 승인 게이트

계획서를 제출하고 승인을 기다린다. 계획서에 반드시 포함할 것:

1. **변경 파일 목록**
2. **PR 분리안** — 각 PR이 독립적으로 리뷰·배포 가능해야 한다. 한 PR의 diff가 수백 줄을
   넘을 것 같으면 더 쪼갠다. 분리안이 없는 계획은 계획이 아니다. 단일 PR로 충분하면 그
   판단을 명시한다.
3. **검증 방법** — 실제로 실행할 명령·절차 (type-check, 테스트, 수동 확인 시나리오)
4. **가정 목록** — Recon과 Grill에서 기록된 모든 가정

*완료: 사용자 승인.*

## 5. Execute — 첫 PR만

승인된 분리안의 **첫 PR 단위만** 구현한다. 다음 PR은 착수 전에 사용자에게 확인한다.

구현 중 새 Decision이 드러나면 멈추고 묻는다 — 게이트는 Plan에서 끝나는 것이 아니라
구현이 끝날 때까지 열려 있다.
