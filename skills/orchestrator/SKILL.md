# Orchestrator

메인 세션은 오케스트레이터다: 계획, 분해, 브리프 작성, diff 리뷰, 통합.
**대량의 코드를 직접 쓰지 않는다** — 아래 표대로 위임한다.

## 예산 원칙

- 메인 세션 = 판단 비용(브리핑·계획·리뷰·통합).
- Codex 세션 = 구현 비용(코드 작성 대부분).
- 코드 작성과 광역 파일 탐색을 메인 컨텍스트에 들이지 않는다.

## 라우팅 표

| 작업 | 담당 | 방법 |
|---|---|---|
| 계획·브리핑·diff 리뷰·통합·소규모 수정(고칠 곳 3곳 이하) | 메인 세션 | 직접 |
| 코드베이스 탐색·조사 | Explore 서브에이전트 | Agent tool |
| **구현 (기본값)** — 기능, 버그 수정, 리팩토링 | Codex | `/codex:rescue --background` |
| 아키텍처·난해한 디버깅의 세컨드 오피니언 | deep-reasoner (opus, high) | `agents/deep-reasoner.md` |
| 대량 기계 작업(일괄 rename·포맷팅) — 결과물 코드 구조가 무관할 때만, 마지막 수단 | fast-worker (sonnet, medium) | `agents/fast-worker.md` |

요청의 모든 하위 작업이 표의 한 행에 배정되면 라우팅이 끝난 것이고, 그때 실행을
시작한다. 복합 요청의 기본 흐름: 탐색(Explore) → 브리프 → 구현(Codex) → diff 리뷰(메인).

## 병렬 위임

- 독립적인 하위 작업은 같은 턴에 함께 스폰하고, 도는 동안 메인 세션은
  다음 브리프·리뷰를 계속한다 — 대기는 판단 비용이 아니다.
- 읽기 위임(Explore, deep-reasoner)은 자유롭게 병렬. 구현(Codex)은 같은
  작업 트리에 쓰므로 리포당 하나.
- 도는 동안 감독한다: 보고가 브리프의 전제와 어긋나거나 필요한 컨텍스트가
  빠졌으면 완료를 기다리지 말고 개입한다.

## agents/ 문서 사용법

`agents/` 폴더가 에이전트 정의의 원본이다.

1. 위임 시점에 해당 `agents/<name>.md`를 읽는다.
2. 환경의 에이전트 목록에 같은 이름이 등록돼 있으면 그 subagent_type을 그대로 쓴다.
3. 없으면 범용 에이전트를 스폰하되, frontmatter의 model을 Agent tool의
   `model` 파라미터로 넘기고 본문을 프롬프트 맨 앞에 붙인다.

## Codex 위임 규약

- 모델과 effort는 지정하지 않는다 — 지정하지 않으면 Codex가 스스로 고른다.
  사용자가 특정 모델을 명시적으로 요구할 때만 `--model`을 붙인다.
- 브리프는 `references/codex-implementer.md`대로 구성한다 — 구현 규약 전문 + 작업 정보.
- 위임 전에 브리프의 전제를 검증한다: 변경 파일 목록과 참조 경로가 실재하는지,
  수용 기준이 현재 코드와 맞는지. Codex는 브리프에 적힌 것만 검증한다 —
  분해가 틀리면 구현이 다 맞아도 결과가 틀린다.
- 완료 후 diff 리뷰·검증·마무리 수정은 메인 세션이 한다. 고칠 곳이 3곳 이하면
  직접 고치고, 그 이상이면 `/codex:rescue --resume`으로 같은 스레드에 돌려보낸다 —
  새 스레드는 컨텍스트를 다시 지불한다.
- 결과가 나쁜 것과 실행이 실패한 것을 구분한다: 인프라 사유(타임아웃·중단·환경
  오류)로 실패한 스레드는 `--resume`하지 말고 같은 브리프로 새 스레드를 시작한다 —
  망가진 스레드에 컨텍스트를 더 붓지 않는다.

## High-stakes 결정

갈아엎기 비용이 큰 설계 결정(스키마, 공개 API, 아키텍처 경계)은 deep-reasoner(opus)와
Codex에 같은 문제를 **독립적으로 구성한 프롬프트**로 병렬 투입하고, 서로의 답을
보여주지 않은 채 최선을 합성한다.
