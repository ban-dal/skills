# PR Template

## 작성 절차

### 1. 근거 수집

PR 내용을 작성하기 전에 저장소에서 다음 정보를 확인한다.

```bash
git status --short
git branch --show-current
git log --oneline <base>..HEAD
git diff --stat <base>...HEAD
git diff --check <base>...HEAD
```

- 커밋 해시, 변경 파일, 테스트 결과, 브랜치 이름을 추측하지 않는다.
- 사용자가 커밋까지 요청했다면 변경을 작업 단위로 나눈다.
- dirty worktree에서는 관련 파일만 명시적으로 스테이징한다. `git add -A`로 사용자의 무관한 변경을 섞지 않는다.
- 각 커밋 전에 `git diff --cached --check`와 staged diff를 확인한다.
- 커밋 후 남은 변경이 있다면 무엇을 제외하고 보존했는지 사용자에게 알린다.

### 2. base 브랜치 결정

- 사용자가 지정한 base 브랜치를 최우선으로 사용한다.
- epic 모델을 사용하는 저장소에서는 현재 작업과 관련된 상위 epic 브랜치를 사용한다.
- 이름이 비슷하다는 이유로 관련 없는 epic 브랜치를 선택하지 않는다.
- 관련 base를 확인할 수 없으면:
  - PR 메시지만 작성할 때는 `<상위 epic 브랜치 지정 필요>`로 남긴다.
  - 실제 PR을 생성할 때는 사용자에게 base를 확인한 뒤 진행한다.

### 3. 검증 근거 확인

- 저장소의 실제 스크립트와 실행 로그를 기준으로 검증 항목을 작성한다.
- 명령이 성공한 항목만 `[x]`로 표시한다.
- 커밋 훅의 staged-file lint만 통과했다면 전체 lint를 통과한 것으로 쓰지 않는다.
- 테스트 개수와 수동 확인 결과는 로그에서 확인된 경우에만 적는다.
- 실행하지 못한 검증은 `[ ]`로 남기고 이유나 확인된 대체 범위를 하위 bullet로 설명한다.

### 4. PR 본문 작성

PR 제목은 `<type>: <요약>` 형식으로 본문과 분리해 작성한다.

```markdown
## 개요

- <!-- 이 PR이 무엇을 왜 하는지 1~2개 bullet로 요약합니다. -->

## 변경 사항

- **<실제 커밋 제목>** (`<짧은 커밋 해시>`)
  - 사용자에게 보이는 변경
  - 구조·정책·테스트 변경
  - <!-- UI 변경이면 관련 스크린샷을 이 항목 아래에 첨부합니다. -->

## 맥락

- 브랜치: `<head>` → `<base>`
- 관련 계획/이슈: 없음

## 검증

- [ ] type-check (`<실제로 실행할 명령어>`)
- [ ] lint (`<실제로 실행할 명령어>`)
- [ ] 단위 테스트 (`<실제로 실행할 명령어>`)
- [ ] 수동 확인:
  - 확인한 경로·상태·결과

## 리뷰 포인트

1. **<리뷰어가 집중할 경계 또는 의사결정>**
   - 배경/의도
   - 이번 PR에 포함된 범위와 제외된 범위

## 후속 작업

- 없음

## 참조 링크

- 없음
```

### 5. 최종 대조

본문을 전달하거나 PR을 생성하기 전에 다음을 확인한다.

- 모든 커밋 해시가 실제 `<base>..HEAD` 범위에 존재한다.
- 변경 사항 설명이 해당 커밋 diff로 증명된다.
- PR에 포함되지 않은 작업을 완료된 것처럼 쓰지 않는다.
- 검증 체크 상태가 실제 실행 로그와 일치한다.
- 후속 작업과 의도적으로 제외한 범위가 리뷰 포인트와 모순되지 않는다.
- 로컬 파일 경로를 GitHub 스크린샷 링크처럼 넣지 않는다.

## 작성 규칙

- **제목**: `<type>: <요약>` 형식을 사용한다.
  - type은 변경 성격에 맞게 `feat`, `fix`, `chore`, `refactor`, `docs`, `test`, `ci`, `perf`, `build` 중 선택한다.
- **개요**: 제목을 반복하지 말고 사용자 가치와 작업 목적을 1~2개 bullet로 요약한다.
- **변경 사항**:
  - base에서 HEAD 방향의 작업 순서대로 그룹핑한다.
  - 커밋 제목과 짧은 해시를 그대로 사용한다.
  - 세부 항목은 화면, 동작, 정책, 테스트처럼 리뷰 가능한 사실로 작성한다.
  - 커밋이 아직 없다면 해시를 만들지 말고 논리적 작업 축으로만 묶는다.
- **맥락**: head와 base 방향을 명확히 쓰고, 관련 이슈가 없으면 `없음`으로 채운다.
- **검증**: 실제 명령어와 수동 확인 대상을 함께 적는다.
- **리뷰 포인트**:
  - 리뷰어가 판단해야 할 경계, 트레이드오프, 의도적인 정적 구현을 우선한다.
  - 단순 변경 사항을 반복하지 않는다.
  - 1~3개로 제한한다.
- **후속 작업**: 이번 PR 범위 밖의 기능만 적고, 없으면 `없음`으로 채운다.
- **스크린샷**:
  - UI 변경이 있을 때만 관련 커밋 항목 아래에 인라인으로 첨부한다.
  - 업로드 URL이 없으면 `<!-- 스크린샷을 첨부해 주세요. -->` 주석을 남긴다.
- **빈 섹션 유지**: 해당 없는 섹션도 삭제하지 않고 `없음`으로 채운다.
- **문체**: 존칭체와 짧은 bullet을 사용한다. 과장된 표현과 긴 서술을 피한다.
- **생성 표식 금지**: PR 본문과 커밋에 `Co-Authored-By`, `Generated with ...` 등 AI 생성 흔적을 남기지 않는다.

## 실행 규칙

- 사용자가 PR 메시지만 요청하면 제목과 본문만 작성하고 push나 PR 생성은 하지 않는다.
- 사용자가 PR 생성을 명시적으로 요청한 경우에만 push와 `gh pr create`를 수행한다.
- 실제 PR 생성 시 `--base`와 `--head`를 모두 명시한다.

```bash
gh pr create \
  --base <상위-epic-브랜치> \
  --head <작업-브랜치> \
  --title "<type>: <요약>" \
  --body-file <PR-본문-파일>
```

## 최종 전달 형식

사용자가 커밋과 PR 메시지를 함께 요청한 경우 다음 순서로 전달한다.

1. 생성한 커밋의 짧은 해시와 제목
2. 실행한 검증과 결과
3. 커밋에서 제외하고 보존한 변경
4. 복사 가능한 PR 제목과 본문

## 주의사항

- `.github/pull_request_template.md`는 생성하지 않는다. 이 스킬의 고정 구조를 사용한다.
- 전역 설정과 충돌하더라도 co-author·AI 생성 표식 금지 규칙을 우선한다.
