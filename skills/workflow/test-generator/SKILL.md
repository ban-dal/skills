# Test Generator Workflow

테스트 작성 작업의 **Workflow(실행 계획)**를 설계한다. 테스트를 찍어내는 게 아니라, **무엇을 검증할 가치가 있는지**와 **어느 수준에서 검증할지**를 먼저 정한다. 커버리지 숫자를 올리려고 자명한 코드까지 테스트하면 유지보수 부채만 쌓인다 — 검증 가치가 순서를 정한다.

공통 원칙·형식은 단일 출처를 따른다(설계 전에 읽는다):

- [`../workflow-architect/references/principles.md`](../workflow-architect/references/principles.md) — 순서 규칙, Task 분해 기준, 검증 메뉴
- [`../workflow-architect/references/agent-strategy.md`](../workflow-architect/references/agent-strategy.md) — 병렬 판단, Agent Task Card
- [`../workflow-architect/references/output-contract.md`](../workflow-architect/references/output-contract.md) — 출력 형식

## 이 유형의 고유 절차

공통 순서 위에서, 테스트 작성은 아래를 추가로 한다.

1. **테스트 대상과 명세 식별** — 무엇의 *어떤 행동*을 잠그는가. 검증할 행동을 *관찰 가능한 결과*로 적는다 — 반환값만이 아니라 상태 변화·부수 효과(저장·전송·이벤트)·협력자 호출·예외/에러까지. 관찰할 수 없는 건 테스트할 수 없다.
   - *완료*: 대상별 "이 상황에서 이 행동을 하면 이 결과가 관찰된다" 명세 목록이 있다.
2. **핵심 동작과 엣지 케이스 분리** — 정상 경로(핵심 계약)와 경계·실패 경로(빈 값·경계값·동시성·권한 없음·예외)를 나눈다. 가치 순으로 핵심부터.
   - *완료*: 핵심/엣지 케이스가 분리·정렬돼 있다.
3. **테스트 수준 판단(Unit/Integration/E2E)** — 각 동작을 가장 싸게 잠그는 수준을 고른다: 순수 로직은 Unit, 모듈 간 계약은 Integration, 사용자 흐름은 E2E. 같은 것을 여러 수준에서 중복 검증하지 않는다.
   - *완료*: 케이스마다 검증 수준과 그 이유가 붙어 있다.
4. **기존 테스트 스타일 분석** — 프로젝트의 테스트 프레임워크·구조·네이밍·assertion 관례를 먼저 읽고 *그대로 따른다*. 새 스타일을 들여오지 않는다(프로젝트에 테스트 네이밍 규칙이 있으면 그 규칙을 따른다).
   - *완료*: 따를 프레임워크·패턴·네이밍 규칙이 적혀 있다.
5. **테스트 구현 계획과 검증** — 케이스를 테스트 Task로 묶고, 완료 기준은 "테스트가 실제로 의미 있게 실패할 수 있는가"다. 항상 통과하는(대상을 끄든 켜든 그린인) 테스트는 무가치하다.
   - *완료*: "대상 동작을 깨면 해당 테스트가 빨개진다"가 검증 완료 기준이다.

## Decision Point

- **테스트하기 어려운가?** → 즉시 리팩터로 점프하지 말고 *원인부터 분류*한다: ⓐ 강결합·숨은 의존(싱글턴·전역) → 이음새(seam)를 내는 리팩터를 선행 Task로(refactor), ⓑ 진짜 외부 의존이 필요 → 무리한 mocking 대신 수준을 Integration으로 올린다, ⓒ 행동 자체가 불명확 → 1단계 명세로 되돌아간다, ⓓ 테스트 인프라(하네스·프레임워크) 부재 → 셋업 Task를 선행으로. 원인에 맞는 처방을 고른다.
- **버그를 고치려는 건가, 옳은 동작을 잠그려는 건가?** → *현재 깨진 동작*을 드러내는 실패 테스트로 수정을 몰고 가려는 거면 그건 bugfix의 재현 테스트다 → bugfix에 넘긴다. 여기(test-generator)는 *옳다고 보는 동작*을 잠그고 커버리지를 보강하는 일이다.
- **레거시에 테스트가 전무한가?** → 위험·변경 빈도 높은 곳부터 특성화 테스트로 그물을 친다(전부 한 번에 덮으려 하지 않는다).
- **대상이 서로 독립적인가?** → 모듈별로 병렬 Agent로 나눠 작성하고 합친다(agent-strategy.md). 단, 테스트는 *공유 테스트 인프라*(fixture·mock·factory·setup/teardown·스냅샷·시드 DB)에서 충돌하기 쉽다 — 공유 인프라를 건드리면 그 변경을 선행 셋업 Task나 "머지 후" Task로 격리하고 그 위에서만 병렬화한다.

## 출력

[`output-contract.md`](../workflow-architect/references/output-contract.md) 형식으로 이 테스트 작업의 Workflow를 출력한다. 검증 항목은 "추가된 테스트가 의미 있게 실패할 수 있음 + 기존 테스트 무손상"으로 채운다.

## Anti-pattern

- ❌ 커버리지 숫자만 올리려 자명한 코드까지 테스트한다(부채만 증가).
- ❌ 무엇을 보장하는지 모른 채 테스트부터 찍는다(명세 없는 테스트).
- ❌ 항상 통과하는 테스트 — 대상을 깨도 빨개지지 않으면 검증이 아니다.
- ❌ 프로젝트 관례를 무시하고 새 테스트 스타일을 들여온다.
