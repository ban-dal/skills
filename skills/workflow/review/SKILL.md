# Review Workflow

코드 리뷰 작업의 **Workflow(실행 계획)**를 설계한다. 리뷰는 코드를 고치는 게 아니라, **변경을 판정**하는 일이다. 리뷰가 가장 자주 실패하는 지점은 둘 — 의도를 모른 채 스타일만 지적하거나, 사소한 것과 머지를 막아야 할 것을 같은 무게로 쏟아내는 것. Workflow가 이 순서를 강제한다.

공통 원칙·형식은 단일 출처를 따른다(설계 전에 읽는다):

- [`../workflow-architect/references/principles.md`](../workflow-architect/references/principles.md) — 순서 규칙, 리뷰 단위 기준, 검증 메뉴
- [`../workflow-architect/references/agent-strategy.md`](../workflow-architect/references/agent-strategy.md) — 병렬 판단, Orchestration Gate, Agent Task Card
- [`../workflow-architect/references/output-contract.md`](../workflow-architect/references/output-contract.md) — 출력 형식

## 이 유형의 고유 절차

공통 순서 위에서, 리뷰는 아래를 추가로 한다.

1. **변경 의도 파악** — 이 변경이 *무엇을 달성하려는가*를 먼저 잡는다(PR 설명·커밋·연결된 이슈). 의도를 모르면 코드가 옳은지 판정할 수 없다. 의도가 비면 그것부터 묻는다.
   - *완료*: 변경의 목표가 1줄로 적혀 있다.
2. **위험 영역 식별** — diff에서 가장 위험한 곳을 먼저 고른다(인증·결제·데이터 마이그레이션·동시성·공개 API·삭제). 리뷰 노력을 위험 순으로 배분한다 — 모든 줄을 같은 강도로 보지 않는다.
   - *완료*: 위험 순으로 정렬된 검토 대상 목록이 있다.
3. **관점별 리뷰** — 정렬된 대상을 다음 관점으로 본다: **스펙 충족**(1단계 의도를 다 구현했나 + *요청 안 한 동작이 들어오지 않았나*(scope creep)), **정확성**(엣지·실패 경로), **설계**(결합도·중복·일관성), **보안**(입력 검증·권한·비밀), **유지보수**(가독성·테스트). 관점마다 근거를 코드 위치에 붙인다.
   - *완료*: 각 지적이 파일·라인과 "왜 문제인가"에 묶여 있고, 스펙 미충족·범위 초과가 별도로 표시돼 있다.
4. **Actionable 코멘트화** — 각 지적을 *무엇을 어떻게 바꾸라*는 실행 가능한 제안으로 바꾼다. "이상함"이 아니라 "X일 때 Y로 터지니 Z로 가드하라".
   - *완료*: 모든 코멘트가 구체적 액션을 담고 있다.
5. **Blocker / Suggestion / Nit 분류** — 각 코멘트를 *결과* 기준으로 아래 표에 따라 라벨링한다. 경계가 모호하면 더 무거운 쪽으로. 이 분리가 없으면 리뷰가 노이즈가 된다.

   | 라벨 | 기준 (결과) | 예 |
   |---|---|---|
   | **Blocker** | 머지되면 안 됨 — 정확성·보안·데이터 손상·스펙 미충족·범위 초과 | 인증 우회, 데이터 유실, 요구사항 누락 |
   | **Suggestion** | 머지는 가능, 개선하면 좋음 — 설계·유지보수 | 중복, 더 나은 추상화 |
   | **Nit** | 취향·사소한 일관성, 무시 가능 | 네이밍 선호, 포맷 |

   - *완료*: 모든 코멘트가 위 세 라벨 중 하나를 갖고, "머지 가능 여부"(Blocker 0건 = 가능) 판정이 있다.

## Decision Point

- **리뷰를 분리할 수 있는가?** → 관점(스펙·보안·…)이나 파일 영역이 서로 독립적이면 축별 병렬 Agent로 나누고(축끼리 컨텍스트 오염 방지) 결과를 합친다. 크기가 아니라 **분리 가능성**이 기준이다(agent-strategy.md).
- **의도가 불명한가?** → 추측으로 지적하지 말고 의도 확인을 선행한다. 잘못된 전제의 리뷰는 해롭다.
- **테스트가 없는 변경인가?** → 2단계의 위험 영역(정확성·보안·데이터·동시성)에 테스트가 없으면 **Blocker**, 저위험 영역이면 **Suggestion**. 어느 쪽이든 빠진 검증이 무엇인지 명시한다.

## 출력

[`output-contract.md`](../workflow-architect/references/output-contract.md) 형식을 따르되, 산출물의 핵심은 **Blocker / Suggestion / Nit으로 분류된 actionable 코멘트 목록 + 머지 가능 여부 판정**이다. 코드를 직접 고치지 않는다 — 수정이 필요하면 해당 작업 유형 Skill로 넘긴다.

## Anti-pattern

- ❌ 의도를 모른 채 스타일·취향만 지적한다.
- ❌ Blocker와 Nit을 같은 무게로 쏟아 리뷰를 노이즈로 만든다.
- ❌ "여기 이상함" 같은 실행 불가능한 코멘트를 남긴다.
- ❌ 리뷰하랬더니 코드를 직접 고쳐버린다(리뷰의 책임 경계를 넘는다).
