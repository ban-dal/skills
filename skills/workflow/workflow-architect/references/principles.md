# 공통 Workflow 원칙

`workflow-architect`와 모든 하위 실행 Skill이 따르는 단일 출처. 어떤 타입의 작업이든 이 원칙은 동일하다.

## 철학 — Workflow Engineering

- **Prompt Engineering** — 모델의 사고를 제어한다. 모델이 바뀌면 결과가 흔들린다.
- **Workflow Engineering** — 작업의 흐름을 제어한다. Claude Code든 Codex든 Cursor든, 같은 작업은 같은 *프로세스*를 거친다.

코드를 직접 작성하는 것이 목적이 아니라, 작업을 어떤 순서·규칙으로 진행할지를 설계하는 것이 목적이다.
산출물은 이 작업에 바로 쓰는 **Workflow(실행 계획)**이며, 재사용 Skill 파일을 만드는 것이 아니다.

## 순서가 곧 규칙이다

이 사슬을 항상 같은 순서로 따른다. 앞 단계를 건너뛴 뒤 단계는 신뢰하지 않는다.

```
문제·목표 → Task 분해 → 의존성 분석 → 병렬 가능성 → Agent 책임 → 리뷰 단위 → 검증
```

- 구현보다 **계획**을 먼저 만든다.
- 계획보다 **Task**를 먼저 정의한다.
- 병렬화보다 **의존성**을 먼저 분석한다.
- Agent를 나누기 전에 **파일 범위**를 먼저 정한다.
- "완료"는 **구현 완료**가 아니라 **검증 완료**를 뜻한다.

## Task 분해 기준

Task는 다음을 모두 만족해야 한다. 하나라도 못 지키면 더 쪼갠다.

- 하나의 명확한 목표만 가진다.
- 독립적으로 리뷰 가능하다.
- 독립적으로 테스트 가능하다.
- 완료 기준이 명확하다.
- 다른 Task와 충돌 가능성이 낮다(변경 파일 범위가 겹치지 않는다).
- 변경 파일 범위를 예측할 수 있다.

너무 크면 다시 분할하고, 너무 작아 의미 없으면 합친다. Task 개수나 코드 라인 수를 하드코딩하지 말고, 요구사항과 위험도에 따라 판단한다.

## 리뷰 단위 기준

리뷰는 사람이 한 번에 검토할 수 있는 단위를 목표로 한다. 변경 범위·영향도·위험도·리뷰 난이도·테스트 가능성을 보고 단위 크기를 정한다. 이 중 하나라도 리뷰를 어렵게 만들면 Task를 다시 쪼갠다.

## 검증 메뉴

목표는 구현 완료가 아니라 **검증 완료**다. 작업 성격에 맞는 것만 고른다.

| 검증 | 언제 |
|---|---|
| 테스트 | 거의 항상 |
| 회귀 검증 | 기존 동작을 건드릴 때(리팩터링·버그 수정) |
| 성능 확인 | 성능 개선·핫패스 변경 |
| 보안 확인 | 인증·입력 처리·외부 노출 변경 |
| 수동 QA | 자동화가 어려운 UX·통합 경로 |
