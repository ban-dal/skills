# 의존성·병렬·Agent 전략

병렬은 목적이 아니라 결과다. Agent를 많이 만드는 것이 아니라, 먼저 의존성을 분류한다.

## 의존성 분류

- **병렬 가능** — 선행 의존성이 없고, 파일 범위가 서로 겹치지 않는다.
- **순차 필수** — 한 Task의 출력이 다른 Task의 입력이다.
- **머지 후** — 선행 구현 의존성 없이 독립 설계할 수 있지만, 병렬 산출물이 모인 뒤 단독으로 적용·검증해야 하는 통합 작업(예: 공유 인터페이스 정리, 라우팅 통합).

## Orchestration Gate

Workflow 설계자는 실행 전에 Orchestration Mode가 필요한지 판정한다. 이 판정은 책임 분리와 독립 검증을 위한 Workflow 규칙이다.

다음 사전 신호 중 하나라도 있으면 Orchestration Mode를 사용한다:

- Task가 4개 이상으로 분해된다.
- 독립 구현·검증 책임 범위가 2개 이상 나온다.
- 라우팅·상태·API 계약·테스트 중 2개 이상이 함께 바뀐다.
- 새 도메인 또는 새 사용자 플로우를 만든다.
- 외부 API·generated type·SDK·mock 계약이 변경되거나 새로 도입되고, 영향이 2개 이상의 독립 구현·검증 책임 범위에 전파된다.
- CONVENTION.md·architecture docs 같은 규칙 문서를 강하게 따라야 한다.

다음 진행 중 신호는 Orchestration Mode로 전환하는 tripwire다. 파일 수와 라인 수는 사전 확정 조건이 아니라 작업 중 관찰값이다:

- 실제 변경 파일이 10개를 넘었다.
- 생성 코드를 제외한 손작성 코드가 대략 500줄을 넘었다.
- 같은 규칙 또는 같은 파일 범위의 규칙 위반을 정정받았다.
- 계획에 없던 Task가 2개 이상 추가됐다.
- context 압축, handoff, 장시간 세션이 필요해졌다.

Orchestration Mode에서 main agent는 직접 구현을 기본으로 하지 않고 Task 분해·위임·산출물 통합·최종 검증을 소유한다. 필요한 역할만 분리하되, Plan 작성·Plan 리뷰·구현·테스트 작성·코드 리뷰는 서로 다른 책임으로 취급한다. 실행 환경이 sub-agent를 지원하지 않으면 같은 책임 경계를 순차 세션 또는 수동 단계로 실행한다.

병렬 가능 판단은 다음을 모두 만족할 때만 "예"다:

- Task 간 의존성이 낮다.
- 수정 파일 충돌 가능성이 낮다.
- 각 Agent의 책임이 명확하다.
- 각 Agent 결과를 독립적으로 검증할 수 있다.
- 병렬 완료 후 통합 검증 계획이 있다.

하나라도 어긋나면 병렬을 포기하고 순차로 강등하거나 Task를 다시 쪼갠다.
병렬 가능 Task를 순차로 실행하려면 Workflow에 이유를 적는다.

## Agent Task Card

위임 또는 병렬 작업마다 아래 8필드를 채운다. 빈 칸이 있으면 그 Agent는 아직 투입할 수 없다.

```
목적          — 이 Agent가 끝내야 할 한 가지
입력          — 시작 시 주어지는 것(파일·계약·전제)
관련 규칙      — 적용할 규칙 문서 경로와 섹션명(없으면 "없음"; 전문 첨부 금지)
수정 가능 범위 — 건드려도 되는 파일/디렉터리
수정 금지 범위 — 절대 건드리면 안 되는 것(다른 Agent 소유)
완료 조건      — 체크 가능한 종료 기준
검증 방법      — 완료를 어떻게 확인하는가
예상 산출물    — 끝났을 때 남는 것(PR·파일·변경)
```

Task Card는 충분한 task-local context만 담는다. 관련 규칙 필드에는 규칙 문서 전문을 붙이지 말고, 파일 경로와 섹션명만 준다. Agent는 작업 전에 그 섹션을 직접 읽고 적용할 규칙만 짧게 메모한다.

Agent 간 공유 상태는 파일 시스템의 명시적 산출물로만 교환한다. 코드 변경, 테스트 결과, 리뷰 메모, handoff 문서가 공유 상태다. 채팅 맥락이나 main agent의 암묵적 기억에 의존하지 않는다.

구현 Agent를 쓰지 않더라도 Orchestration Mode이거나 규칙 민감 작업이면 review Agent를 둔다. review Agent는 구현하지 않고 규칙 위반, 불필요한 추상화, 파일 분해 과잉, 테스트 누락만 찾는다.
