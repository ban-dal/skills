# 명확화 게이트 (Clarification Gate)

코드를 *수정*하는 작업(`implement-feature` · `bugfix` · `refactor`)은 Workflow 설계에 들어가기 전
이 게이트를 **0단계**로 통과해야 한다. 모호한 한 줄 요청이 그대로 Task 분해로 직행하는 것을 막는 안전장치다.

순서는 둘이다: **domain-modeling → grilling**. 도메인을 먼저 알고, 그래도 남는 빈칸만 캐묻는다.

## 1. domain-modeling — 묻기 전에 안다

캐묻기 *전에* `llm-wiki` 스킬의 Query 모드로 프로젝트·도메인 컨텍스트를 먼저 끌어온다
(`~/Documents/wiki/index.md` → 관련 문서). wiki에 이미 적힌 컨벤션·구조·과거 결정을 다시 묻지 않기 위해서다.

끌어온 컨텍스트로 작업 도메인의 작은 모델을 세운다:

- **핵심 개념·엔티티** — 이 작업이 다루는 대상은 무엇인가.
- **기존 컨벤션·제약** — wiki·코드에 이미 정해진 규칙(있으면).
- **영향 경계** — 이 변경이 닿는 모듈·계약·사용자.

*완료*: 끌어온 컨텍스트 요약 + "이미 아는 것 / 아직 모르는 것" 목록이 갈라져 있다.

## 2. grilling — 남는 빈칸만 캐묻는다

domain-modeling 후에도 **모를 때만** 발동한다. 아래 통과 조건이 이미 충족되면 게이트를 통과시키고
바로 Workflow 설계로 넘어간다 — 명확한 요청까지 매번 캐묻지 않는다.

**통과 조건(모두 충족 시 grilling 생략):**

- 수용 기준 / 수정 완료 기준이 "X 하면 Y" 형태로 체크 가능하게 적힌다.
- 범위 경계가 정해진다 — *무엇을 하지 않는지*가 명시된다.
- 핵심 엣지·실패 케이스가 식별된다.

하나라도 비면 그 빈칸만 골라 캐묻는다. 캐물을 후보 메뉴:

| 캐물을 것 | 빈칸의 예 |
|---|---|
| 목표·수용 기준 | "되게 해줘"인데 무엇이 "됨"인지 미정 |
| 범위 경계 | 어디까지 손대고 어디부터 안 건드리는지 미정 |
| 입력·데이터 형태 | 입력 종류·형식·규모가 불명 |
| 엣지·실패 케이스 | 빈 값·동시성·권한 없음 등 미고려 |
| 제약 | 성능·보안·하위 호환 요구가 불명 |
| 우선순위 | 여러 요구 중 무엇이 먼저인지 미정 |

*완료*: 빈칸이 메워져 통과 조건을 충족하거나, 사용자가 "그 부분은 네 판단대로"라고 위임했다.

## 규칙

- **빈칸이 메워지기 전엔 Task 분해로 넘어가지 않는다.** 이 게이트가 닫혀 있으면 뒤 단계를 신뢰하지 않는다.
- **한 번에 묶어 묻는다.** 질문을 한 개씩 난사하지 말고, 빈칸을 모아 한 라운드로 캐묻는다.
- **wiki에 이미 있는 건 묻지 않는다.** domain-modeling이 grilling의 범위를 좁힌다.
- 사용자가 명시적으로 위임하면 그 항목은 통과로 친다(추측한 가정은 Workflow에 기록한다).
