# Work Logger

## 하나의 파일, 브랜치의 생애

- 경로: `{작업 repo}/.claude/logs/{브랜치명}.md` (`/` → `-`로 치환). **브랜치 1개 = PR 1개 =
  로그 1개.** 브랜치명으로 파일을 찾으므로, 생애주기 어느 시점에 트리거돼도 새 파일을 만들지
  않고 같은 파일을 이어 쓴다. 없을 때만 새로 만든다.
- **로컬 스캐폴드다.** `.claude/logs/`를 작업 repo의 `.gitignore`에 넣는다(항목이 없으면
  추가한다). 팀 공유는 PR 본문(pr-template)이 담당하므로, 이 로그엔 존칭체·co-author 규칙을
  적용하지 않는다.

## 트리거와 행동

각 트리거는 파일의 다른 부분만 건드린다.

| 시점 | 행동 |
|---|---|
| **Plan 확정** (dev-briefing) | 파일 생성 + 승인된 계획서 원문을 `## 계획`에 그대로 박제. 휘발 방지 앵커. |
| **구현 중 수정** | Plan과 어긋난 변경을 `## 변경 이력`에 append. **아키텍처·설계 변경은 반드시.** |
| **PR 생성 요청** | `## 작업 사항`을 완성해 pr-template의 재료로 넘김. Account 검증. 주 트리거. |
| **PR open 후 리뷰 반영** | 리뷰어 지적으로 인한 변경을 `## 변경 이력`에 append(아키텍처 변경 필수). 필요 시 PR 본문도 동기화. |

## 문서 구조

골격(계획·변경 이력·작업 사항)은 늘 존재하고, 나머지는 내용이 있을 때만 만든다.
`## 사람이 반드시 리뷰할 변경`은 비어도 `없음`으로 남긴다. 주석은 작성 지침이므로 생성된
로그엔 남기지 않고 헤더와 내용만 둔다. 조각으로 쓰되, 이 대화를 못 본 다음 에이전트가
로그만으로 브랜치를 재구성할 수 있어야 한다 — diff·계획을 그대로 옮기지는 않는다.

```markdown
# {제목}

- branch: {branch} → base: {base}
- 생성: {YYYY-MM-DD}
- 링크: {기획 / Figma / 이슈}

## 계획
<!-- Plan 확정 시 dev-briefing 승인 계획서 원문: 변경 파일 목록 · 작업 분리안 ·
     검증 방법 · 가정 목록. 이 블록은 이후 수정하지 않는다 —
     계획과 실제의 차이는 아래 변경 이력이 담는다. -->

## 변경 이력
<!-- append-only. Plan 이후 벌어진 일. 최신 항목을 맨 위에. -->
- [YYYY-MM-DD][구현|PR리뷰] {무엇을 바꿨나} — 이유: {왜} / 영향: {어디에}
  <!-- 아키텍처 · 설계 · 공개 인터페이스 · 스키마 변경은 생략 불가 -->

## 작업 사항
<!-- PR 생성 시 완성. diff를 나열하지 말고 리뷰어·다음 에이전트가 읽을 작업 단위로 묶는다. -->
-

## 사람이 반드시 리뷰할 변경
<!-- 비즈니스 로직 · 공통 컴포넌트/함수 · 신규 규칙. 강제 섹션 — 없으면 `없음`. -->
없음

<!-- 아래 두 섹션은 내용이 있을 때만 만든다. -->

## 수동 검증
<!-- PR 트리거 시 필수. 재현 방법과 함께 checkbox로. -->
- [ ]

## 리팩터 요청 (승격 후보)
<!-- 사용자가 AI 생성 코드에 요청한 리팩터. 반복되면 repo의 CONVENTION.md로 승격. -->
-
```

## Account (종료 전 검증)

- 모든 diff가 `## 작업 사항`의 어느 단위엔가 포함됐는지 확인한다. 누락 파일은 별도로 명시한다.
- `## 사람이 반드시 리뷰할 변경`이 비어있지 않은지 확인한다 — 항목이 없으면 `없음`이 적혀 있어야 한다.
- 생성된 로그에 작성 지침 주석(`<!-- -->`)이 새어 들어가지 않았는지 확인한다.
- PR 생성 트리거였다면: `## 작업 사항`·`## 수동 검증`이 pr-template의 "변경 사항"·"검증"
  섹션으로 옮겨졌는지 확인한다.
