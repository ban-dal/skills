# /interview-me — 요구사항 인터뷰

사용자의 모호한 아이디어나 요청을 실행 가능한 요구사항, 해결 방향, Spec으로 구체화한다.

목표는 오래 인터뷰하는 것이 아니라, 필요한 만큼만 질문하고 빠르게 실행 가능한 형태로 정리하는 것이다.

## 원칙

- 먼저 사용자의 요청을 현재 이해한 내용으로 짧게 요약한다.
- 질문은 한 번에 하나씩 한다.
- 답을 코드베이스, 문서, README, 기존 구현에서 확인할 수 있다면 먼저 확인한다.
- 단, 코드베이스 탐색은 필요한 범위에서만 수행한다. 최근 commit 확인은 변경 의도나 이력이 중요할 때만 한다.
- 작은 작업을 불필요하게 큰 설계 프로세스로 확장하지 않는다.

## 진행 방식

### 1. 현재 이해 요약

다음을 3~5줄로 정리한다.

- 사용자가 달성하려는 목표
- 현재 불명확한 부분
- 확인이 필요한 핵심 의사결정

### 2. 컨텍스트 확인

필요할 때만 다음을 확인한다.

- 관련 파일 / 폴더
- README / llm-wiki / docs / convention 문서
- 기존 구현 패턴
- 최근 변경 이력

코드나 문서를 확인했다면, 어떤 근거로 판단했는지 짧게 설명한다.

### 3. 핵심 질문

질문은 하나씩 한다.

우선순위는 다음과 같다.

1. 목표: 무엇을 달성하려는가?
2. 사용자/대상: 누가 사용하는가?
3. 범위: 이번 작업에 포함/제외할 것은 무엇인가?
4. 제약: 기술, 일정, 디자인, 정책 제약은 무엇인가?
5. 완료 기준: 무엇이 되면 끝났다고 볼 수 있는가?
6. 영향 범위: 어떤 화면, API, 컴포넌트, 문서에 영향을 주는가?

가능하면 질문과 함께 2~3개의 선택지를 제시한다.

각 선택지에는 장단점과 추천안을 짧게 적는다.
항상 "직접 입력"도 허용한다.

### 4. 요구사항 정리

충분히 이해했다면 다음 형식으로 정리한다.

- 목표
- 배경 / 문제
- 포함 범위
- 제외 범위
- 제약 조건
- 완료 기준
- 예상 영향 범위
- 미결정 사항
- 가정한 내용

### 5. 해결안 / Spec 제시

난이도에 따라 필요한 만큼만 작성한다.

작은 작업이면 간단한 bullet spec으로 충분하다.
큰 작업이면 다음 섹션으로 나눈다.

- 사용자 흐름
- 화면 / UI 요구사항
- 상태 / 데이터 흐름
- API / 서버 연동
- 에러 / 예외 처리
- 접근성 / 반응형 / 성능
- 테스트 기준
- 마이그레이션 또는 롤아웃 계획

### 6. 셀프 리뷰

Spec을 제시하기 전에 빠르게 점검한다.

- 모순되는 요구사항은 없는가?
- 여전히 모호한 표현은 없는가?
- 영향 범위가 과소평가되지 않았는가?
- 작은 작업을 과하게 키우지 않았는가?
- 사용자가 바로 판단할 수 있을 만큼 구체적인가?

### 7. 사용자 승인

작업 실행 전에는 최종 Spec을 보여주고 확인을 요청한다.

단, 사용자가 명시적으로 "바로 진행", "알아서 정리", "가정하고 해줘"라고 한 경우에는
가정을 명시한 뒤 바로 실행 계획으로 넘어간다.

### 8. 실행 계획

Spec이 확정되면 plan mode를 사용해 실행 계획을 세운다.

실행 계획에는 다음을 포함한다.

- 작업 순서
- 수정 대상 파일
- 검증 방법
- 리스크
- 되돌리기 쉬운 단위

## 출력 형식

기본 출력은 짧고 명확하게 작성한다.

권장 형식:

1. 현재 이해
2. 확인한 컨텍스트
3. 질문
4. 선택지
5. 임시 가정
6. 정리된 Spec
7. 실행 계획

항상 모든 섹션을 출력할 필요는 없다.
상황에 맞게 필요한 섹션만 사용한다.
